# 세대현관 `0x1E` 실측 시나리오

작성 2026-08-30. 사용자가 세대현관부터 시험 가능하다고 했고, 본인이 유일한 테스터입니다.
착수 전 검수를 위한 문서입니다.

## 1. 먼저 알아야 할 것 — 이 시나리오의 전제 하나가 이미 무너졌습니다

사용자가 제안한 순서는 이랬습니다.

1. 호출 버튼 눌러서 **호출 상태 감지**
2. 호출 On일 때 문열기 송신 후 문열림 감지
3. 호출 Off일 때 문열기 시도

**1번이 이 회선에서는 불가능합니다.**

### 1.1 `0x1E`에는 상태가 없습니다

44,986 프레임을 전수 조사했습니다. `0x1E` 프레임은 **딱 두 종류**뿐입니다.

| 프레임 | 종류 | 횟수 |
| --- | --- | ---: |
| `f70b011e016211000091ee` | 질의 | **4,865** |
| `f70e011e024311040004ffffb6ee` | 설정 (문열기) | 3 |

**질의 4,865개가 전부 바이트 단위로 동일합니다.** 상태를 실을 자리가 움직인 적이
없습니다. 다른 기기들처럼 응답이 따로 오지도 않습니다.

### 1.2 벨이 울린 순간에도 버스는 조용합니다

원본 캡처에 문열기 명령이 121.9·122.6·123.1초에 세 번 있습니다. 누군가 벨을 눌렀고
사용자가 문을 열어 준 순간입니다. **그 앞뒤로 여덟 기기 가운데 무엇도 바뀌지
않았습니다.**

20초 창에서 드문 프레임은 문열기 자신(3회)과, 19초 뒤의 승강기 호출 하나뿐입니다.
문을 열고 승강기를 부른 자연스러운 순서입니다.

**즉 벨 호출은 이 회선에 나타나지 않습니다.** 월패드가 내부에서 처리하고, 회선에는
결과인 문열기 명령만 내놓습니다. 복도 승강기 버튼이 회선에 안 나타난 것과 같은 구조입니다.

**따라서 "호출 On/Off"를 우리가 구분할 수 없습니다.** 사용자가 말로 알려주는 수밖에
없습니다.

## 2. 레거시가 알려주는 것 두 가지

### 2.1 레거시는 이 프레임을 **보내지 않습니다**

`Include/Define/DoorLock.py`에 `makePacketOpen()`이 있고, 그 바이트가 우리가 관측한
것과 정확히 같습니다.

```
F7 0E 01 1E 02 43 11 04 00 04 FF FF B6 EE
```

그런데 그것을 보내는 `ThreadCommandQueue.set_doorlock_open()`이 **통째로 주석
처리되어 있습니다.** 레거시는 문을 **GPIO 핀**으로 엽니다. 라즈베리파이 핀을 내려
5초간 열림을 유지하는 방식입니다.

**그러므로 이 프레임은 레거시에서도 검증된 적이 없습니다.** 정의만 있고 쓰이지
않습니다. 우리가 가진 유일한 근거는 **월패드가 실제로 세 번 보낸 것**입니다.

### 2.2 레거시의 진짜 문열기는 서브폰 매크로입니다

```python
def makePacketOpenFrontDoor(self):    # 0xB4
    # 현관 초인종 카메라 영상이 서브폰으로 우회된 상태에서 도어락 해제
def makePacketOpenCommunalDoor(self):  # 0x61
    # 공동현관문 호출 후 카메라 영상이 우회된 상태에서 열림 명령
```

**주석이 사용자의 모델과 일치합니다.** 호출이 걸려 영상이 우회된 상태여야 열립니다.

다만 **이 회선에 `0x7F`는 44,986 프레임 중 0회**입니다. 서브폰 경로는 여기에 없거나
다른 배선입니다. 그리고 서브폰은 이번 작업의 범위 밖입니다.

## 3. 그래서 실제로 시험할 수 있는 것

| 사용자 제안 | 가능 여부 |
| --- | --- |
| 호출 상태 감지 | **불가.** 이 회선에 신호가 없음 (§1) |
| 호출 On일 때 문열기 송신 | 가능. 다만 "On"은 사용자가 알려줘야 함 |
| 호출 Off일 때 문열기 시도 | 가능. **가장 중요한 시험** |

**3번이 핵심입니다.** 호출이 없을 때도 문이 열린다면, 그 프레임은 이 회선에 접근할 수
있는 누구든 문을 열 수 있다는 뜻입니다. 애드온이 그것을 노출할지 말지가 달라집니다.

## 4. 이 시나리오가 요구하는 결정

**`0x1E 02`는 지금 영구 거부 목록에 있습니다.** 어떤 단계로도, `--allow-all`로도 열리지
않습니다. 가스 열기와 `0x7F` 매크로와 같은 칸에 있습니다.

```typescript
if (device === 0x1e && kind === 0x02) {
  return "the 0x1E 02 frame's meaning is undecided and may be a door-open command";
}
```

**이 거부를 여는 것은 단계를 넓히는 것과 성격이 다릅니다.** 지금까지의 승인은 "이 목록에
이 프레임을 추가한다"였는데, 이번은 "절대 보내지 않기로 한 것을 보낸다"입니다.

거부 문구가 "meaning is undecided and **may be** a door-open command"라고 적혀 있는데,
이제 그 불확실성은 해소되었습니다. **레거시가 `makePacketOpen`이라고 이름 붙였고**,
캡처에서 문이 열리는 순간에 나왔습니다. **문열기 명령이 맞습니다.** 거부의 근거였던
"미상"이 사라졌으니, 남는 것은 "문을 여는 것이 위험한가"라는 판단뿐입니다.

## 5. 단계

### A단계 — 벨 관측, 위험 없음

| 단계 | 내용 | 누가 |
| --- | --- | --- |
| A1 | 관측 창을 열고 기준선 확인 | 도구 |
| A2 | **세대현관 벨을 누름** | 사용자 |
| A3 | 20초간 버스 전체를 관측 | 도구 |

**예측: 아무것도 나타나지 않습니다.** §1.2가 그렇게 말합니다. 예측이 맞으면 "호출은
회선에 없다"가 관측 두 건으로 굳어집니다. **틀리면 그것이 발견입니다.**

위험 없음. 사용자가 자기 집 벨을 누르는 것뿐입니다.

### B단계 — 호출 없는 상태에서 문열기 송신

**여기서 거부 목록을 엽니다.**

| 단계 | 내용 |
| --- | --- |
| B1 | 사용자가 **문 앞에 서서** 준비 |
| B2 | 호출이 없는 것을 확인 (벨을 누르지 않은 상태) |
| B3 | `f70e011e024311040004ffffb6ee` **1회** 송신 |
| B4 | 사용자가 문이 열렸는지 확인하고 알려줌 |
| B5 | 버스에 무엇이 응답했는지 기록 |

**판정**
- 열리면: 이 프레임은 호출과 무관하게 문을 엽니다. **보안상 중요한 사실**이고, 애드온
  설계가 달라집니다.
- 안 열리면: 호출 중에만 유효하다는 뜻입니다. C단계로 갑니다.

**위험**: 문이 잠깐 열립니다. 사용자가 문 앞에 있으므로 통제됩니다. 캡처의 월패드는
**세 번 연속**(0.7초 간격) 보냈는데, 우리는 **한 번만** 보냅니다. 한 번으로 안 되면
그 자체가 정보입니다.

### C단계 — 호출 중 문열기 (B가 실패했을 때만)

| 단계 | 내용 | 누가 |
| --- | --- | --- |
| C1 | 벨을 누르고 **호출 중이라고 알려줌** | 사용자 |
| C2 | 같은 프레임 1회 송신 | 도구 |
| C3 | 문이 열렸는지 확인 | 사용자 |
| C4 | 필요하면 캡처처럼 3연속(0.7초 간격) 재시도 | 도구 |

## 6. 중단 조건

- **A단계에서 예상 밖의 프레임이 나오면 멈추고 먼저 해독합니다.** 벨 신호가 있다면
  그것부터 아는 편이 낫습니다.
- **B단계에서 문이 열리면 C단계는 하지 않습니다.** 답이 나왔고, 문을 더 열 이유가
  없습니다.
- 사용자가 문 앞에 없으면 B·C를 하지 않습니다.

## 7. 이 시나리오가 답하지 않는 것

- **공동현관.** 이번 범위 밖입니다. 사용자가 세대현관부터라고 했습니다.
- **서브폰 `0x7F` 경로.** 범위 밖이고 이 회선에 0회입니다.
- **문이 얼마나 오래 열려 있는지.** 레거시의 GPIO는 5초를 유지하지만 그것은 다른
  방식입니다. 이 프레임이 유발하는 시간은 모릅니다.
- **프레임의 필드 의미.** 여섯 바이트(`04 00 04 FF FF`)가 무엇인지 모릅니다. 관측된
  것이 전부 같은 값이라 변화를 볼 수 없었습니다.
