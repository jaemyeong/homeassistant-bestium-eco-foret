# EW11 프레이밍과 그룹 프레임 분석 · `capture-1788009200284`

작성: 2026-08-29 (Asia/Seoul)

근거는 두 가지입니다. 하나는 사용자가 EW11 웹 설정의 `Serial Port Settings` 화면을
찍어 주신 것이고, 다른 하나는 같은 시각에 애드온으로 뜬 54.6분짜리 캡처
`capture-1788009200284.ndjson`입니다. 캡처는 **제품 디코더를 전혀 부르지 않는 독립
파서**로 해석했습니다. 파서가 아는 규칙은 길이 바이트, 마지막 두 바이트를 제외한
XOR, 종결자 `EE` 뿐입니다.

---

## 0. 한 문장 요약

EW11의 `Gap Time`이 50 ms라는 사실이 확정되어 **TCP 도착 시각과 RS485 유휴 사이의
간격이 처음으로 수치화되었고**, 같은 캡처에서 **조명과 난방의 전체 끄기 단일 프레임이
관측되어** "버스에도 레거시에도 일괄 난방 명령은 없다"는 기존 명세의 서술이 반증되었습니다.

## 2. EW11 설정 · 미검증에서 확정으로

사용자가 읽어 주신 `Serial Port Settings` 화면의 값입니다.

| 항목 | 값 |
| --- | --- |
| Baud Rate | 9600 |
| Data Bit / Stop Bit / Parity | 8 / 1 / **None** |
| **Buffer Size** | **512 바이트** |
| **Gap Time** | **50 ms** |
| Flow Control | Disable |
| Protocol | None |
| Cli | Serial String `+++`, Waiting Time 300 |

8N1이므로 한 바이트가 10비트를 차지하고, 9600 baud에서 **1바이트는 1.042 ms,
11바이트 프레임은 11.46 ms**입니다.

`Gap Time` 50 ms의 뜻은 이렇습니다. EW11은 시리얼 회선이 **50 ms 동안 조용해져야**
모아둔 바이트를 TCP로 밀어냅니다. `Buffer Size` 512바이트는 11바이트 프레임 46개에
해당하므로 실제로는 도달하지 않고, 언제나 시간 조건이 먼저 걸립니다.

### 2.1 이 값이 캡처에서 확인됩니다

- 읽기 사이 간격의 **98.6%가 50 ms 이상**입니다. 50 ms 미만인 1.4%는 EW11이 한 번
  밀어낸 것을 TCP 계층이 두 조각으로 나눈 경우로 설명됩니다.
- **읽기의 20%가 프레임을 두 개 이상 담고 있습니다.** 질의와 그 응답이 전선에서
  50 ms 안에 끝나면 한 번에 밀려 나오기 때문입니다. 실제로 그 예가
  `f70b011b0143110000b5ee`(가스 질의)와 `f70d011b04431100040000b2ee`(그 응답)처럼
  질의·응답 쌍입니다.

### 2.2 따라서 우리가 보는 것은 전선이 아닙니다

읽기가 시각 `T`에 도착했다면 그 프레임의 마지막 바이트는 전선에서 **약 `T − 50 ms`**에
끝났습니다. 원장이 `M4-E111`에 "busy-line 게이트가 TCP 도착시각을 RS485 유휴로
오인한다"고 적어 둔 것의 정확한 크기가 이제 나왔습니다. **50 ms입니다.**

## 3. 충돌 위험 곡선

읽기가 `T`에 도착한 뒤 `X` ms 뒤에 11바이트를 쓴다면, 그 11.46 ms 동안 월패드의
전송과 겹칠 확률을 캡처 전체에 대해 계산했습니다. 전선 위 버스트의 위치는
`[T − 50 − D, T − 50]`으로 재구성했습니다. `D`는 그 읽기가 담은 바이트 수가 차지하는
시간입니다.

| 쓰기 지연 `X` | 충돌률 | 쓸 수 있던 기회 |
| ---: | ---: | ---: |
| 0 ms | 39.9% | 17,560 |
| 10 ms | 40.8% | 17,535 |
| 20 ms | 13.1% | 17,516 |
| **30 ms** | **6.0%** | **17,480** |
| 40 ms | 13.0% | 17,435 |
| 50 ms | 14.5% | 17,316 |
| **60 ms (현재 기본값)** | **19.2%** | 16,892 |
| 80 ms | 7.2% | 9,926 |
| 100 ms | 5.7% | 9,580 |
| 150 ms | 0.7% | 7,559 |

읽기가 도착한 뒤 다음 버스트가 시작되기까지의 시간은 중앙값 42.0 ms이고, 4분의 1은
4.5 ms 안에 시작합니다.

### 3.1 이 표를 읽는 법

**`X`가 커질수록 기회가 줄어듭니다.** 150 ms 열의 7,559건은 전체의 43%뿐이며, 그것도
원래 조용하던 구간만 남은 것입니다. 그러므로 큰 `X`의 낮은 충돌률은 선택 편향이
섞여 있고 액면 그대로 비교할 수 없습니다.

편향 없이 비교할 수 있는 구간에서 보면 **30 ms가 6.0%로 가장 낮고, 기회도 99.5%를
유지합니다.** 현재 기본값인 60 ms는 19.2%로 세 배 이상 높으면서 기회도 더 적습니다.

### 3.2 이것은 가설이지 결론이 아닙니다

세 가지 이유로 아직 결론이 아닙니다.

1. **모형이 `Gap Time` 50 ms에 지터가 없다고 가정합니다.** 실제로는 재구성한 버스트의
   7.2%가 직전 읽기보다 먼저 시작한 것으로 나오는데, 이는 물리적으로 불가능하므로
   수 ms 규모의 지터가 존재한다는 뜻입니다. 곡선은 그만큼 뭉개져 있습니다.
2. **무선 지연의 변동을 반영하지 않았습니다.**
3. **사용자의 실측과 어긋납니다.** 사용자는 20 ms보다 60 ms가 낫다고 관측하셨는데,
   이 곡선은 20 ms(13.1%)가 60 ms(19.2%)보다 낫다고 말합니다. 다만 그 관측은 `0.2.8`
   빌드에서 이루어졌고 원장이 그 시점에 서로 다른 세 기제가 함께 작동하고 있었다고
   기록해 두었으므로, 개선이 충돌 때문이었는지는 분리되지 않았습니다.

**이 불일치를 가르는 것이 `buslab`의 존재 이유입니다.** 도구는 매 송신마다 확보한
유휴 시간을 기록하므로, 위 곡선이 예측하는 형태가 실제로 나오는지 직접 확인할 수
있습니다. 그때까지 `tx_quiet_ms`는 60 ms로 둡니다.

## 4. 그룹 프레임 두 개 · 기존 명세의 반증

이 캡처에는 사용자가 월패드를 직접 조작한 구간이 있고, 거기에 **설정 명령 16개**가
들어 있습니다. 기존 캡처에는 조명 설정 명령이 하나도 없었습니다.

### 4.1 조명 전체 끄기

```
F7 0B 01 19 02 40 10 02 00 B4 EE
```

주소 `0x10`은 개별 조명(`0x11`·`0x12`·`0x13`)이 아니라 그룹입니다. 상태 응답이
이것을 증명합니다.

| 시각 | 사건 | 그룹 응답의 조명 상태 |
| --- | --- | --- |
| +77.2s | | `01 01 02` |
| +78.5s | **`f70b01190240100200b4ee` 송신** | |
| +79.4s | | **`02 02 02`** |
| +80.3s | `f70b01190240110100b6ee` 송신 (조명 1 켜기) | |
| +81.4s | | `01 02 02` |

전체 끄기 한 프레임으로 세 조명이 모두 꺼졌고, 이어진 개별 켜기로 조명 1만 켜졌습니다.

### 4.2 난방 전체 끄기 · **명세가 틀렸습니다**

```
F7 0B 01 18 02 46 10 04 00 B5 EE
```

| 시각 | 사건 | 네 존의 상태 |
| --- | --- | --- |
| +88.8s | | `01 01 01 01` |
| +92.2s | **`f70b01180246100400b5ee` 송신** | 같은 읽기의 응답이 `04 04 04 04` |
| +92.9s | | **`04 04 04 04`** |

`.agent/spec-device-protocol.md`와 `bestium-eco-foret/src/protocol-debug.ts`의 주석은
모두 "버스에도 레거시 구현에도 일괄 난방 명령은 없다"고 적고 있습니다.
**그 서술은 이 캡처로 반증되었습니다.** 월패드 자신이 단일 프레임으로 네 존을 끕니다.

현재 제품은 전체 끄기를 존별 네 프레임으로 펼쳐서 보냅니다. 각 프레임은 월패드의
것과 바이트 단위로 같으므로 개별로는 유효하지만, 반이중 버스에 연속으로 네 개를
밀어 넣는 것은 한 개를 보내는 것보다 충돌에 훨씬 취약합니다. 사용자가 "전체난방끄기
동작안함"이라고 보고하신 것과 일치하는 방향입니다.

### 4.3 관측되지 않은 것

**그룹 켜기는 관측되지 않았습니다.** 조명도 난방도 주소 `0x10`에 켜기 값을 보내는
프레임은 캡처에 없습니다. 끄기만 근거가 있습니다.

## 6. 응답 지연 · 조명과 난방이 다릅니다

| 기기 | 명령에서 응답까지 | 관측 |
| --- | --- | --- |
| 난방 | **50 ms 미만** | 여섯 건 모두 같은 TCP 읽기에 담김 |
| 가스 | **50 ms 미만** | 같은 읽기 |
| 조명 | **약 55~68 ms** | 여섯 건 모두 다음 읽기에서 도착 |

50 ms는 `Gap Time`이 만드는 바닥입니다. 그보다 짧은 지연은 TCP에서 구분할 수
없습니다. 조명만 그 문턱을 넘었다는 것은 **조명 응답이 난방보다 실제로 느리다**는
뜻이며, 프레임 길이(11.46 ms)를 빼면 전선에서 명령이 끝난 뒤 약 44~57 ms 뒤에 응답이
시작된 것으로 계산됩니다. 몇 건이 50 ms 아래로 나오는 것은 §3.2의 지터로 설명됩니다.

이 값은 애드온의 `tx_observation_timeout_ms` 3,000 ms가 지나치게 넉넉하다는 것을
뜻하지만, **직접 응답이 아니라 폴링 응답으로 확인되는 경로를 함께 좁히기 전에는
줄이면 안 됩니다.** 원장의 `P2-C`가 그 위험을 이미 기록해 두었습니다.

## 7. `0x1E 02`는 여전히 미결입니다

`+121.9s`, `+122.6s`, `+123.1s`에 `f70e011e024311040004ffffb6ee`가 세 번 나옵니다.
이전 캡처와 **바이트 단위로 같습니다.** 그리고 **어떤 응답도 뒤따르지 않습니다.**

문열기 명령인지 호출 종료 알림인지는 이 캡처로도 갈리지 않습니다.
`.agent/analysis-0.2.8-field-report.md` §1.7이 요구한 두 가지 판별 캡처가 여전히
필요합니다.

## 8. 이 분석이 바꾸지 않은 것

**제품 코드는 한 줄도 바꾸지 않았습니다.** 그룹 프레임 두 개는 관측되었지만 우리가
보낸 적은 없고, 충돌 곡선은 모형에 근거한 가설입니다. 둘 다 `buslab`으로 전선에서
확인한 뒤에 제품에 반영하는 것이 순서입니다. `.agent/plan-buslab.md`의 Epic E4가
그 확인 절차입니다.

---

## 9. 남은 공백

- 그룹 **켜기** 프레임은 관측되지 않았습니다.
- 조명 **끄기**와 난방 **끄기**의 개별 프레임은 이 캡처에 없습니다.
- 충돌 곡선은 `Gap Time` 50 ms에 지터가 없다고 가정하며, 재구성의 7.2%가 물리적으로
  불가능한 배치를 내므로 그 가정이 정확하지 않다는 것이 이미 드러나 있습니다.
- 조명 응답이 난방보다 느린 이유는 모릅니다.
- 사용자의 20 ms 대 60 ms 관측과 곡선이 어긋나며, 아직 어느 쪽도 기각되지 않았습니다.
