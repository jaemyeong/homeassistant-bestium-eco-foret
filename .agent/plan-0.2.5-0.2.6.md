# 0.2.5 · 0.2.6 계획

작성: 2026-08-25 (Asia/Seoul)

## 0. 확정된 진단

조명 버튼이 동작하지 않은 원인은 전송 경로가 아니라 **화면 흐름**이었다.

- 사용자 확인: RX 모니터링은 정상, RAW 임의 전송으로 조명 1이 켜짐 → 소켓·EW11·월패드·프레임 바이트 모두 정상.
- 사용자 확인: "검토 및 확인 카드가 있는 줄 몰랐다" → 두 번째 활성화를 누른 적이 없다.
- 현재 구현은 모든 제어가 2단계다. 조명 버튼은 미리보기만 만들고, 전송은 페이지 아래 별도 카드의 확인 버튼이 필요하다.
- 정본 프로토타입의 상호작용 로직은 `toggle → write()`로 **원탭**이다. 3단계는 임의 전송 실험실(RAW) 하나뿐이다.

부수적으로, 커밋을 막는 조건은 19개인데 그중 6개(`readinessRevision` 불일치, `previewReady`,
`observedRevalidated` 대기, `pendingChallenge` 바인딩, `statusInvalid`, evidence별 enable)는
화면에 전혀 표시되지 않는다. `readinessRevision`은 `rxByteEpoch`·`readEpoch`·`validFrameEpoch`·
`tailHash`를 해시에 넣으므로 수신 바이트마다 바뀐다.

## 1. 사용자 결정 사항

| 항목 | 결정 |
| --- | --- |
| 관측된 제어의 활성화 | **정본대로 원탭.** RAW만 3단계 유지 |
| 0.2.5 범위 | **네 화면 전부** — 데스크톱 제어면, 모바일 390px, 디버그면, 배너 7상태 |
| 0.2.6 검증 | 조명 1로, 내가 Chrome을 조작해 전송하고 상태 프레임 확인까지 보고. 끈 뒤 원상 복구 |

원탭 전환은 가스 닫기·현관 열기·승강기 호출에도 적용된다. 사용자가 "가스·현관·승강기만
2단계 유지" 선택지를 명시적으로 물리치고 정본을 택했다.

## 2. 지난 실패에 대한 설계 원칙

| 실패 | 이번 계획의 대응 |

## 3. 0.2.5 — UI 개편

정본: `~/Downloads/BESTIUM 월패드 웹 UI-handoff.zip` 안의
`bestium-ui/project/Bestium Wallpad UI.dc.html`, `SendBanner.dc.html`, `_ds/**`.

### 3.1 상호작용 계약 변경

- 조명, 난방(관측 확인/추측 후보), 승강기, 출입구, 가스: **원탭 전송**.
- RAW 임의 전송: 1 미리보기 → 2 확인 → 3 전송 3단계 유지.
- 2단계 활성화를 고정하던 기존 테스트를 새 계약으로 다시 쓴다. `readyForAction`이
  false를 반환하는 19개 조건 전부에 **한국어 사유 문자열**을 붙이고, 막힌 컨트롤 옆과
  배너에 표시한다. 사유 없이 조용히 막히는 경로를 남기지 않는다.

### 3.2 화면

**A1 데스크톱 제어면** — 헤더(아이콘, `BESTIUM 월패드`, `백양산 베스티움 에코포레 · RS485 ·
애드온 <버전>`, EW11 상태 chip, 새로 고침) → 탭(제어/디버그) → SendBanner → 조명 3타일
+ 스위치 → 난방(관측 확인 Zone 1 / 추측 후보 Zone 2-4 분리, 큰 현재 온도, 목표
number-buttons 5–40°C, 켜기·끄기, 추측 후보 숨김) → 공용부·안전(승강기 상행·하행,
출입구 세대·공동 현관, 가스 닫기).

**A2 모바일 제어면** — 폭 390px, 같은 내용을 세로로.

**A3 디버그면** — 패킷 수집(시작·중지·내려받기 + 수집 시간·기록·수신 바이트·저장 파일 +
파일명 줄) → 수신 프레임 로그 테이블(계열·16진수·해석·경과) → 조회 전용 기기(콘센트
0x1F, 환기 0x2B) → 미확인·모호 묶음 → 임의 전송 실험실(경고 + 3단계).

**A4 배너 7상태** — off / quiet / ready / sending / confirmed / unconfirmed / doorbell.

### 3.3 서버 쪽에 필요한 것

- `confirmed` / `unconfirmed`: 전송 결과를 배너까지 배선한다. 지금은 `outcome` 텍스트로만 끝난다.
- `doorbell`: 출입구 호출 프레임 관측을 배너 상태로 올린다.
- 프레임 로그의 `계열`·`해석`: `debug.frames`에 계열 라벨과 해석 문자열을 더한다.

### 3.4 하지 않을 것 하나

정본 헤더는 EW11 게이트웨이의 실제 주소와 포트를 그대로 보여 준다. 그러나 현재 상태 DTO는
`/ew11|host|port|user|challenge|token/i` 키를 의도적으로 삭제한다. 이 편집(redaction)은
기록된 보안 결정이므로 조용히 되돌리지 않는다. 헤더에는 주소 없이
`EW11 게이트웨이 · TCP · 연결됨`만 표시한다. 주소를 노출하려면 별도 결정이 필요하다.

### 3.5 수용 기준 (사용자가 직접 확인)

1. 사이드바 패널을 열면 헤더·탭이 있는 새 화면이 뜬다.
2. 제어 탭에서 조명 스위치를 한 번 누르면 **바로 전송**되고, 배너가
   `보낸 뒤 응답을 관측하고 있습니다` → `요청한 상태를 확인했습니다` 또는
   `소켓으로 보냈지만 요청한 상태는 관측하지 못했습니다`로 말한다.
3. 디버그 탭에 프레임 로그 테이블과 임의 전송 실험실 3단계가 보인다.
4. 어떤 컨트롤이 막혀 있으면 **왜 막혔는지 한국어 문장**이 그 자리에 있다.
5. 390px 폭으로 줄여도 레이아웃이 무너지지 않는다.

## 4. 0.2.6 — 실제 TX 검증

0.2.5가 공개되고 사용자가 애드온을 업데이트한 뒤에 시작한다.

1. 캡처를 시작하고 게이트가 열리는 것을 확인한다.
2. Chrome으로 제어 탭에서 **조명 1 스위치**를 한 번 누른다.
3. 다음을 동시에 기록한다 — 배너 상태 전이, `POST /api/action` 네트워크 요청과 응답,
   콘솔 오류, 조명 1 타일의 상태 줄, 프레임 로그에 나타나는 0x19 상태 프레임.
4. 물리 결과를 사용자에게 확인받는다.
5. 원래 상태로 되돌린다.
6. 막히면 0.2.5에서 만든 사유 표시가 어느 조건인지 지목한다. 그 조건만 고친다.

### 4.1 수용 기준

- 한 번의 스위치 조작으로 프레임이 소켓에 나가고, 그 사실이 네트워크 로그로 남는다.
- 배너가 `confirmed` 또는 `unconfirmed` 중 하나로 끝난다. 조용히 아무 일도 없는 경우가 없다.
- 실패하면 그 이유가 화면에 한국어로 적혀 있다.

## 5. 경계

푸시, Home Assistant 업데이트, 실제 TX는 각각 별도 승인 대상이다. 0.2.6의 조명 1 전송은
이미 승인되었으나 0.2.5 공개와 애드온 업데이트가 선행되어야 한다.
