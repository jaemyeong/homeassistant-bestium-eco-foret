# 0.3.0 설계 · 전송 큐, 재시도, 확인 기준

작성: 2026-08-25 (Asia/Seoul) · 근거: `.agent/analysis-0.2.8-field-report.md`, 원장 `M4-E115`·`M4-E116`

## 0. 이번 시험이 확정한 것

사용자가 `tx_quiet_ms`를 올려 시험한 결과 **조명·가스·난방의 모든 동작을 확인**하셨습니다.
이것은 상관관계보다 강한 **개입 증거**입니다. 유휴 대기 시간을 늘리자 증상이 사라졌으므로,
`M4-E116`이 미해결로 남겨 두었던 충돌 귀속이 확정되었습니다. 저널 대조는 더 이상 필요하지
않습니다.

동시에 난방 승격 조건도 충족되었습니다. `M4-E115`가 요구했던 "현재 상태와 반대되는 상태를
한 번 명령"이 실사용으로 이루어졌습니다.

남은 문제는 세 가지입니다. **간헐적 실패에 대한 재시도**, **한 번에 하나만 나가는 제약을
큐로 흡수하는 일**, 그리고 **승강기·출입구**입니다.

### 0.1 60 ms에서도 남은 실패 · 원인이 하나가 아닙니다

사용자가 적용한 값은 **60 ms**이고, 이 값에서도 **이따금 실패하며 기다렸다가 다시 누르면
된다**고 보고하셨습니다. "기다리면 된다"는 관찰이 중요합니다. 충돌은 시간을 두고 눌러도
같은 확률로 일어나므로, **연달아 누르는 것 자체가 막히는 경로가 따로 있다는 뜻**입니다.

후보가 세 가지이며 셋 다 지금 코드에 실재합니다.

1. **조명 관측 임대의 무음 거부.** `ui.ts:503`이 관측 대기 중인 조명에 대해 같은 조명을
   다시 누르면 **메시지 없이 반환**합니다. 창은 `tx_observation_timeout_ms`(3초)입니다.
   조명 1을 켜고 3초 안에 끄기를 누르면 아무 일도 일어나지 않습니다.
2. **후보 쿨다운.** `speculative_tx_cooldown_ms`(1초)가 챌린지 발급 단계에서 걸리고,
   문구가 쿨다운이라고 말해 주지 않습니다. 난방과 가스가 후보였으므로 여기에 해당합니다.
3. **3초 창의 거짓 실패.** 폴링으로만 확인되는 기기는 중앙값 1.9~2.2초, 최악 6.3초가
   걸리므로 실제로는 성공했는데 3초에 미확인으로 보고될 수 있습니다.

셋 다 **이 문서가 설계하는 큐로 사라집니다.** 1번은 병합이 대신하고(다시 누르면 큐의 값이
바뀔 뿐 버려지지 않습니다), 2번은 쿨다운 자체를 없애며, 3번은 재시도와 서버 확인이 흡수합니다.

그러므로 60 ms에서 남은 실패를 전부 충돌로 보아서는 안 됩니다. 충돌이 얼마나 남았는지는
**60 ms 상태에서 캡처를 켜고 손상 구간을 세어야** 알 수 있으며, 그것은 4절의 재시도가
필요한지 판정하는 근거이기도 합니다.

## 1. "모든 Tx는 Rx로 변경 관측되어야 성공인가"

**변경(change)이 아니라 일치(match)여야 합니다.** 근거가 캡처에 있습니다.

캡처 A에서 우리가 보낸 난방 명령 두 건은 이미 그 상태였던 존을 같은 상태로 명령한
**무동작**이었습니다. 그런데도 월패드는 직접 응답을 냈습니다. 변경을 요구하면 이 두 건은
영원히 실패로 판정되고 재시도가 끝나지 않습니다.

그래서 성공 판정은 세 조건의 곱입니다.

1. 해당 기기의 상태가 **의도한 값과 같을 것**
2. 그 관측이 **쓰기 시각 이후**의 것일 것 (`lastSeenAtMs >= writeAtMs`)
3. 그 관측이 **현재 세대**의 것일 것 (`generation === current`)

2번이 핵심입니다. 무동작 명령이라도 쓰기 이전의 값으로 성공 판정을 내리면 프레임이 충돌로
사라진 경우를 놓칩니다. 쓰기 이후의 관측을 요구하면, 직접 응답이 오면 수십 밀리초 안에,
직접 응답이 없어도 다음 폴링에서 판정이 납니다.

**관측할 상태가 없는 동작은 이 기준을 적용할 수 없습니다.** `0x7F` 출입구 매크로는 이 회선에
응답이 존재하지 않습니다. 성공했다고 말할 근거가 없으므로 별도 결과값
`sent_unconfirmable`로 보고하고 **재시도하지 않습니다.** 문을 여는 프레임을 확인 없이
반복 전송하는 일이기 때문입니다.

### 1.1 술어는 그 의도가 소유한 필드만 봅니다

난방 응답은 하위명령과 무관하게 **존 전체**를 실어 옵니다. 목표 온도 명령(`0x45`)의 응답도
전원 상태를 함께 담고, 전원 명령(`0x46`)의 응답도 현재·목표 온도를 함께 담습니다.

```
+104.3초  f7120118044511180117180000000000baee
                        ↑45  ↑zone ↑명령값 ↑전원 ↑현재 ↑목표
```

그러므로 "해당 존의 응답이 왔다"를 성공으로 삼으면 전원 항목과 온도 항목이 서로의 응답으로
확인되어 버립니다. **각 의도는 자기가 소유한 필드만 봅니다.** 전원은 `state`만, 목표 온도는
`targetC`만 봅니다.

> **미확인 사항**: 목표 온도 명령이 꺼져 있는 존을 켜는지 알지 못합니다. 캡처의 `0x45`
> 두 건은 모두 zone 1이 이미 켜져 있을 때 관측되었습니다. **꺼져 있는 존에 목표 온도를
> 한 번 설정**해 보면 판정이 납니다.

## 2. 확인 술어 표

모든 술어에 1절의 세대·시각 조건이 함께 걸립니다.

| 의도 | 큐 키 | 성공 술어 | 관측 원천 |
| --- | --- | --- | --- |
| 조명 n → s | `light:n` | `lights[n].state === s` | 단일 응답 `0x19 04 40 1n`, 없으면 전체 응답 |
| 난방 z 전원 → s | `heat:z:power` | `heating[z].state === s` | 직접 응답 `0x18 04 46 1z`, 없으면 `0x4A` |
| 난방 z 목표 → c | `heat:z:target` | `heating[z].targetC === c` | 직접 응답 `0x18 04 45 1z`, 없으면 `0x4A` |
| 가스 닫기 | `gas` | `gas.state === "closed"` | `0x1B 04` 폴링 (중앙값 약 1.4초) |
| 승강기 호출 d | `elevator` | `elevator.call === d` | `0x34` 상태 바이트 하위 니블 (6.1절) |
| 콘센트·환기 조회 | `query:<kind>` | 해당 기기 freshness 갱신 | 조회 응답 · 재시도 없음 |
| 출입구 `0x7F` | 큐에 넣지 않음 | 없음 | 없음 · `sent_unconfirmable` |

`heat all off`는 **하나의 다중 프레임 매크로가 아니라 `heat:1..4:power` 네 개의 독립 항목**으로
전개합니다. 월패드 자신도 존별 프레임 네 개를 0.3초에서 2.0초 간격으로 따로 보냅니다.

## 3. 전송 큐

### 3.1 위치

**서버(`m2.ts`)에 둡니다.** 한 번에 하나라는 제약도, 확인에 필요한 RX 해독도 서버에 있습니다.
클라이언트에 두면 새로고침으로 사라지고, 탭이 두 개면 서로 싸웁니다.

### 3.2 자료 구조

```
pending  : Map<key, Intent>     // 삽입 순서 유지 = FIFO
inflight : Attempt | null       // 전역 한 개
```

`Map`이므로 **키 공간 자체가 큐의 상한**입니다. 조명 3 + 난방 8 + 가스 1 + 승강기 1 +
조회 2 = 14개를 넘을 수 없습니다. 별도의 큐 길이 제한이 필요 없습니다.

### 3.3 병합 규칙

같은 키로 다시 들어오면 `Map.set`이 **값만 바꾸고 자리는 유지**합니다. 사용자가 요청하신
"같은 디바이스면 가장 마지막 상태만 인정"이 그대로 됩니다. 자리를 유지하는 이유는 뒤에
들어온 다른 기기의 명령이 앞지르지 않게 하기 위해서입니다.

```
조명1 on → 조명1 off → 조명1 on → 조명1 off
  결과: 항목 하나, 상태 off, 버스 쓰기 한 번
```

이미 전송 중인 항목은 되돌릴 수 없으므로, 같은 키의 새 의도는 `pending`에 들어가 **전송 중인
것이 끝난 뒤** 실행됩니다. 조명 1을 켜는 중에 끄기를 누르면 두 번 나가고 최종 상태는 꺼짐입니다.

대기 중이던 항목이 새 의도로 대체되면 결과값 `superseded`로 보고합니다. 화면에서
"마지막 요청으로 대체됨"으로 보여 사용자가 사라진 것으로 오해하지 않게 합니다.

### 3.4 작업자

```
loop:
  if inflight: wait
  entry = pending.shift()            // 삽입 순서
  if not entry: wait
  주기 하한 대기: 직전 버스 쓰기로부터 tx_cooldown_ms(250 ms)
  attempt(entry)
```

`raw`는 큐에 들어가지 않습니다. 대상이 없어 병합 키를 만들 수 없고, 미확인 프레임을
재시도하는 것은 위험합니다. 지금처럼 한 건씩 명시적으로 처리합니다.

### 3.5 세대 변경

전송 세대가 바뀌면(재접속) **`pending`을 전부 버리고 `inflight`는 `indeterminate`로
끝냅니다.** 끊긴 사이에 버스 상태가 달라졌을 수 있으므로 이어서 보내면 안 됩니다.

## 4. 재시도

### 4.1 한 항목의 시도

```
attempt(entry):
  for n in 1..tx_max_attempts:
    if 더 새로운 의도가 같은 키에 있음: return superseded
    if 이미 술어 충족(쓰기 이후 관측): return confirmed
    유휴 창 대기 → 게이트 재평가 → 쓰기
    writeAtMs 기록
    술어가 참이 될 때까지 최대 tx_observation_timeout_ms 대기
    if 참: return confirmed
  return unconfirmed
```

재시도 전에 술어를 다시 보는 것이 중요합니다. 늦게 도착한 확인을 재전송으로 낭비하지 않습니다.

### 4.2 재시도해도 되는 것

**멱등이고 확인 가능한 동작만** 재시도합니다.

- 조명 켜기·끄기, 난방 전원·목표 온도, 가스 닫기, 승강기 호출은 모두 멱등입니다.
- 콘센트·환기 조회는 멱등이지만 재시도할 이유가 없으므로 1회입니다.
- `0x7F` 출입구와 `raw`는 **재시도하지 않습니다.**

### 4.3 쿨다운의 자리

기존의 `speculative_tx_cooldown_ms`는 후보 연타를 막는 장치였습니다. **병합이 그 일을 대신
합니다.** 연타는 최종 상태 한 번의 실행으로 수렴하므로 쿨다운이 필요 없습니다.

대신 작업자가 **버스 쓰기 사이의 하한**으로 `tx_cooldown_ms`(250 ms)를 지킵니다. 재시도도
같은 하한을 지킵니다. 이렇게 하면 초당 최대 4프레임이므로 월패드 자신의 사용량보다 낮습니다.

`unsafe_tx_cooldown_ms`는 큐에 들어가지 않는 `raw` 경로에 그대로 남습니다.

### 4.4 결과값

| 값 | 뜻 |
| --- | --- |
| `confirmed` | 쓰기 이후 관측에서 술어가 참이 되었습니다 |
| `unconfirmed` | 썼으나 시도 횟수를 다 쓰도록 술어가 참이 되지 않았습니다 |
| `refused` | 게이트가 막아 쓰지 않았습니다. 이유를 함께 보고합니다 |
| `superseded` | 실행 전에 같은 키의 새 의도로 대체되었습니다 |
| `sent_unconfirmable` | 썼으나 확인할 RX 경로가 없습니다 (`0x7F` 전용) |
| `indeterminate` | 쓰기가 도중에 실패했습니다. 조작자 확인이 필요합니다 |

## 5. 다중 프레임 경로 · 남기되 격리합니다

**결정됨**: 사용자가 메인 월패드를 끝낸 뒤 서브폰을 구현하실 계획이므로 `0x7F` 매크로는
지우지 않습니다. 따라서 다중 프레임 경로도 남습니다.

`heat all off`를 네 항목으로 전개하면 다중 프레임을 쓰는 동작은 **`0x7F` 출입구 매크로
하나뿐**이 됩니다. 없애지는 않되 **완전히 격리합니다.**

| 경로 | 쓰기 | 큐 | 재시도 | 확인 | 실패 시 잠금 |
| --- | --- | --- | --- | --- | --- |
| 큐 경로 (조명·난방·가스·승강기·조회) | 항상 한 프레임 | 예 | 예 | 상태 일치 | 없음 |
| 매크로 경로 (`0x7F` 출입구) | 세 프레임 | 아니오 | 아니오 | 불가 | 출입구 계열만 |
| `raw` | 한 프레임 | 아니오 | 아니오 | 불가 | 해당 동작만 |

격리의 요점은 **매크로의 실패가 큐를 건드리지 않는 것**입니다. 지금은 매크로 한 번의
`partial_indeterminate`가 `txRetryLocked`를 켜서 조명까지 포함한 화면 전체를 멈춥니다.
부분 쓰기 뒤 상태를 알 수 없는 것은 **그 출입구 기기**이지 조명이 아니므로, 잠금을
계열 단위로 좁힙니다 (9.4절). 이것은 안전 완화가 아니라 잠금 범위를 원인에 맞추는 일입니다.

`M4-E112`(프레임 간 간격 검사)와 `M4-E113`(잠금 해제 경로 없음)이 나온 코드가 그대로 남으므로,
**이 경로는 서브폰 회선이 실제로 붙기 전까지 사실상 죽은 코드**입니다. 그 사실을 주석으로
남기고, 시험은 계속 유지해 서브폰 작업이 시작될 때 회귀를 잡을 수 있게 합니다.

단일 프레임 쓰기도 소켓 오류로 중간에 실패할 수 있으므로 `indeterminate` 자체는 남습니다.
다만 사용자에게 반드시 보이게 만듭니다 (9.2절).

## 6. 승강기

### 6.1 해독 · 운행과 호출을 분리합니다

현재 해독은 운행 중일 때 호출 니블을 보지 않습니다.

```javascript
const direction = moving === 0x0a ? "up" : moving === 0x0b ? "down" : ...
```

`0xa5`는 "상승 중이며 상행 호출 대기"인데 "up" 하나로 뭉개집니다. **호출이 걸려 있다는 사실이
운행 중에는 화면에서 사라집니다.** 두 필드로 나눕니다.

| 필드 | 원천 | 값 |
| --- | --- | --- |
| `motion` | 상위 니블 | `0`=정지, `0xA`=상승, `0xB`=하강 |
| `call` | 하위 니블 | `0`=없음, `1`=도착, `5`=상행, `6`=하행 |

이 분리가 6.3절의 실험을 가능하게 하는 확인 신호입니다.

### 6.2 층 표시 결함

`floor: payload[7]`이 원시 바이트를 그대로 내보내 지하에서 **177**이 표시됩니다.

| 바이트 | 표시 |
| --- | --- |
| `0x01`–`0x63` | 그 숫자 층 |
| `0xB1`–`0xBF` | `B` + 하위 니블 (**추정**, 표본 `0xB1` 하나뿐) |
| `0x00` | 층 미보고. 마지막 관측층을 함께 적되 현재 값으로 쓰지 않습니다 |
| 그 밖 | 원시 16진수 그대로 |

도착 후 값이 `0x00`이 되는 것은 버스가 실제로 그렇게 보내는 것이므로 우리 결함이 아닙니다.
없는 값을 지어내지 않고 "마지막 관측 4층 · 현재 미보고"로 적습니다.

### 6.3 호출 · 계측된 실험으로 바꿉니다

캡처가 준 것은 음성 증거입니다. 월패드의 호출 버튼을 눌렀는데 `0x34` 설정 명령이 나오지
않았고, 그 시각 전후로 어떤 기기도 새 바이트를 내지 않았습니다. 지금 보내는 프레임은
레거시 설정에서 가져온 추측이며 근거가 없습니다.

그런데 6.1절 덕분에 **판정 신호가 생겼습니다.** 호출이 등록되면 하위 니블이 5나 6이 됩니다.
그래서 호출 버튼을 **한 번 누르면 확답이 나오는 실험**으로 바꿉니다.

```
변형 A  F7 0B 01 34 02 41 10 <05|06> 00 <XOR> EE     레거시 기본값
변형 B  F7 0B 01 34 04 41 10 00 <05|06> <XOR> EE     레거시 대체 정의
```

한 번 누르면 A를 보내고 한 폴링 주기 동안 `call`이 요청한 방향이 되는지 봅니다. 아니면 B를
보내고 다시 봅니다. 둘 다 아니면 **"이 회선에서 승강기 호출은 성립하지 않습니다"**를 화면에
기록하고 그 뒤로는 재시도하지 않습니다.

카드에 결과를 남기므로, 다음 릴리스에서 이 버튼을 지울지 말지가 추측이 아니라 관측으로
정해집니다.

## 7. 출입구

### 7.1 `0x1E 02`의 의미 표기를 고칩니다

지금 이 프레임을 `entrances.household.call = true`로 읽습니다. 사용자가 확인해 주신 사실은
두 가지입니다. 이 표시는 **문열기를 눌렀을 때** 켜지고, **바깥에서 벨을 눌렀을 때는 아무
반응이 없습니다.** 그러므로 "호출 중"이라는 표기는 확실히 틀렸습니다.

`call`을 없애고 **"월패드 문열기 조작 관측"**이라는 사건으로 바꿉니다. 이 프레임이 문을 여는
명령인지, 문이 열려서 호출이 끝났다는 알림인지는 아직 가르지 못했으므로 그 사실을 화면에
그대로 적습니다.

**전송 버튼에 연결하지 않습니다.** 현관문에 관한 프레임을 상관관계 하나로 내보낼 수 없습니다.
가르는 실험은 12절에 있습니다.

### 7.2 공동 현관

`0x1E` 조회 프레임 130개가 전부 같은 바이트이고 호출 시점에도 변하지 않았습니다. 읽을 값이
없으므로 **"이 회선에서 관측되지 않음"**으로 표기합니다. 지금처럼 초기 표시를 값처럼 보여
주지 않습니다.

### 7.3 `0x7F` 매크로 · 남깁니다

**결정됨**: 지우지 않습니다. 메인 월패드를 끝낸 뒤 서브폰을 구현할 예정이므로, 동작 정의와
프레임과 시험을 모두 보존하고 화면에는 왜 지금 못 쓰는지를 적습니다.

#### `sevenFProof` 게이트가 실제로 요구하는 것

이름이 "0x7F를 본 적이 있는가"처럼 읽히지만 조건은 훨씬 좁습니다. `m2.ts:1032`의
`hasCurrentSevenFProof`가 **다섯 가지를 모두** 요구합니다.

1. `0x7F` **시퀀스가 완성된 채로 관측**되었을 것. 디코더가 `sevenFProofByStart`에 등록된
   첫 프레임을 보면 추적을 시작하고, 나머지가 **순서대로 연달아** 와야 완성됩니다.
   중간에 잡음이나 깨진 프레임이 하나라도 끼면 추적이 초기화됩니다.
2. 그 관측이 **현재 전송 세대**의 것일 것. 재접속하면 무효가 됩니다.
3. 관측 시각이 **45초 이내**일 것 (`max(45_000, idle_timeout_ms + tx_write_timeout_ms)`).
4. 관측된 시퀀스의 **동작 이름이 지금 보내려는 동작과 정확히 같을 것**
   (`proof.action === "<target>:<state>"`).
5. 관측된 **세 프레임이 지금 보낼 세 프레임과 바이트 단위로 같을 것.**

즉 이것은 "이 회선이 서브폰 프로토콜을 쓴다"는 증명이 아니라 **"방금 45초 안에 누군가가
이 회선에서 바로 이 시퀀스를 하는 것을 보았다"**는 재생 조건입니다.

이렇게까지 좁게 만든 이유가 있습니다. `0x7F` 프레임에는 **XOR도 길이 필드도 없습니다.**
5바이트 고정에 `7F <헤더> 00 00 EE`뿐입니다. 이 회선이 서브폰 회선이 아니라면, `0x7F` 바이트를
정규 `F7` 버스에 쓰는 것은 남의 프로토콜에 임의의 바이트를 밀어 넣는 일이고, 받는 쪽은 그것을
검사할 방법이 없습니다. 그래서 **증거 없이는 한 바이트도 내보내지 않는다**는 쪽으로 잠갔습니다.

지금 통과할 수 없는 이유도 분명합니다. `0x7F` 프레임이 이 회선에서 관측된 적이 한 번도
없습니다. 앞선 306.8초 캡처에서 0개, 이번 두 캡처 412.1초에서도 0개입니다. 레거시 설정이
RS485 포트마다 `packettype`을 따로 두고 `0`이 정규, `1`이 서브폰이며 포트마다 별도의 EW11
주소를 갖는 것과 맞습니다. **서브폰은 설계상 별개의 물리 회선입니다.**

#### 서브폰 작업 때 먼저 고쳐야 할 결함

`sevenFProofByStart`에 등록된 시작 프레임은 두 개뿐입니다.

```
"7fb90000ee" → household:inactive
"7f5f0000ee" → communal:ringing
```

그런데 제공하는 동작은 세 개이고, **`household:ringing`(`7fb70000ee`로 시작)에 대응하는
항목이 없습니다.** 서브폰 회선이 붙어서 월패드가 초인종 응답 문열기를 수행해도 그 동작에
대한 증적은 영원히 기록되지 않고, 조건 4번에서 막힙니다. **세 버튼 중 하나는 회선이 붙어도
못 씁니다.** 0.3.0에서 고치지는 않되 이 문서와 원장에 남겨 서브폰 작업의 시작점으로 둡니다.

#### 0.3.0에서 하는 일

- 카드에 위 다섯 조건을 사용자 언어로 한 문단 적습니다. 지금은 "호환 증적 게이트가 막고
  있습니다"라고만 되어 있어 무엇을 하면 풀리는지 알 수 없습니다.
- 세 버튼을 남기되 **왜 지금 못 쓰는지와 서브폰이 별도 회선이라는 사실**을 함께 적습니다.
- 매크로 실패가 화면 전체를 잠그지 않도록 잠금 범위를 좁힙니다 (9.4절).

## 8. 증거 등급

사용자가 실사용으로 확인하신 만큼 승격합니다.

| 대상 | 현재 | 0.3.0 | 근거 |
| --- | --- | --- | --- |
| 조명 1–3 켜기·끄기 | `observed` | 유지 | 이전부터 실증 |
| 난방 zone 1–4 전원 | `inferred_candidate` | **`observed`** | 프레임이 캡처와 일치하고 실사용 확인 |
| 난방 zone 1–4 목표 온도 | `inferred_candidate` | **`observed`** | 같음 |
| 가스 닫기 | `inferred_candidate` | **`observed`** | 실사용 확인. 여는 방향은 계속 거부 |
| 승강기 호출 | `inferred_candidate` | `inferred_candidate` | 음성 증거. 6.3절의 실험 |
| 출입구 `0x7F` | `unsafe_candidate` | 7.3절의 결정에 따름 | 회선 미확인 |

승격은 **표에 손으로 적습니다.** 확인 이력을 저장해 자동 승격시키면 등급이 조용히 올라가는
경로가 생기므로 그렇게 하지 않습니다.

승격의 결과로 큐에 들어가는 항목은 전부 `observed`가 되고, 챌린지 절차는 승강기 실험과 `raw`
에만 남습니다.

## 9. 게이트 정리

### 9.1 쓰기 직전 경합 검사 (`m2.ts:1405`)

`initialState`가 **유휴 대기 이전**의 스냅숏이라 대기 중에 바이트가 들어오면 거부됩니다.
비교 항목을 둘로 갈라야 합니다.

- **버립니다**: `rxByteEpoch`, `readEpoch`, `tailHash`. 우리 수신은 정상 동작이지 경합이
  아닙니다. `readEpoch`는 캡처 append에서도 올라갑니다.
- **남깁니다**: `externalTxByteEpoch`, `externalTailHash`. **다른 송신자를 잡아내는 유일한
  장치이며, 이번 세션이 진단한 충돌을 막는 것이 바로 이 한 쌍입니다.** 지우면 안 됩니다.

기준 스냅숏은 유휴 대기가 끝난 직후에 다시 찍고, 게이트 재평가와 쓰기를 그 사이에 붙입니다.

### 9.2 무음 반환 제거 (`ui.ts:501`)

```javascript
if (reviewBusy || captureBusy || ... || txRetryLocked) return;
```

메시지 없이 반환하므로 잠긴 뒤의 모든 탭이 흔적을 남기지 않습니다. **어느 조건으로 막혔는지
반드시 화면에 적고** 잠금 상태라면 해제 버튼을 함께 가리킵니다.

### 9.3 클라이언트 관측 기계 제거

`pendingObservation`, `schedulePendingObservation`, `boundedObservationTimeout`,
`setPendingControlLease`는 서버가 확인을 맡으면 전부 불필요합니다. 조명만 다루던 반쪽짜리
구현이기도 합니다. 삭제합니다.

`setPendingControlLease`는 전송 버튼의 `disabled`를 무조건 `false`로 되돌려 `readyForAction`의
판단을 덮어쓰고 있었으므로, 삭제가 그 결함도 함께 없앱니다.

### 9.4 잠금 범위를 원인에 맞춥니다

`txRetryLocked`는 지금 화면 전체를 멈춥니다. 부분 쓰기 뒤 상태를 알 수 없는 것은 **그 동작이
건드린 기기**이므로, 잠금을 계열 단위로 좁힙니다. 출입구 매크로가 반쯤 나가면 출입구 카드만
잠기고 조명·난방·가스는 계속 씁니다. 잠금은 항상 화면에 드러나며 해제 버튼을 함께 가리킵니다.

### 9.5 화면에 큐를 드러냅니다

대기 항목, 전송 중 항목, 최근 결과를 목록으로 보여 줍니다. 각 항목은 키·의도·시도 횟수·결과를
답니다. 사용자가 "눌렀는데 아무 일도 없다"고 느낄 여지를 없애는 것이 목적입니다.

## 10. 설정

| 이름 | 현재 | 0.3.0 | 비고 |
| --- | --- | --- | --- |
| `tx_quiet_ms` | 20 | **60** | 사용자가 60 ms로 시험해 대부분의 손실이 사라졌습니다 (0.1절) |
| `tx_observation_timeout_ms` | 3000 | 유지 | 확인 창으로 **재사용**합니다. 새 설정을 만들지 않습니다 |
| `tx_max_attempts` | 없음 | **신설 3** | 범위 `int(1,10)` |
| `tx_cooldown_ms` | 250 | 유지 | 의미가 "버스 쓰기 사이 하한"으로 바뀝니다 |
| `speculative_tx_cooldown_ms` | 1000 | **유지, 범위 축소** | 큐에 들어간 제어에는 적용하지 않습니다. 스키마에서 지우면 이미 저장된 설치본의 옵션이 무효가 될 수 있으므로 키는 남기고, 후보 챌린지 발급에만 계속 걸립니다 |
| `unsafe_tx_cooldown_ms` | 5000 | 유지 | `raw` 경로 전용 |

가스 확인은 폴링에만 기대므로 3초 창에서 이따금 놓칠 수 있습니다. 그때는 재시도가 한 번 더
나가고 다음 폴링에서 확인됩니다. 가스 닫기는 멱등이므로 피해가 없습니다. 측정 결과 부족하면
설정값을 올리면 됩니다.

## 11. 시험 (먼저 작성합니다)

1. 병합 · `조명1 on/off/on/off` → 항목 하나, 최종 `off`, 쓰기 한 번
2. 순서 · `조명1 → 조명2 → 조명1 갱신` → 실행 순서가 조명1, 조명2이고 조명1은 갱신값
3. 대체 · 대기 중 항목이 새 의도로 바뀌면 이전 항목이 `superseded`
4. 직접 응답 확인 · 쓰기 뒤 `0x18 04 46 13` 투입 → 재전송 없이 `confirmed`
5. 폴링 확인 · 쓰기 뒤 `0x4A` 전체 응답 투입 → `confirmed`
6. 무동작 확인 · 이미 그 상태인 존에 같은 상태를 명령해도 `confirmed`이며 무한 재시도 없음
7. 오래된 관측 거부 · 쓰기 **이전** 시각의 일치 관측으로는 확인되지 않음
8. 필드 소유 · `heat:z:target` 항목이 `0x46` 전원 응답으로 확인되지 않음
9. 재시도 소진 · 응답을 주지 않으면 `tx_max_attempts`회 쓴 뒤 `unconfirmed`
10. 세대 변경 · 대기 항목이 비워지고 전송 중 항목이 `indeterminate`
11. 전개 · `heat all off`가 `heat:1..4:power` 네 항목이 됨
12. 승강기 해독 · `0xA5` → `motion=up, call=up`, `0xB6` → `motion=down, call=down`, `0x01` → `call=arrival`
13. 층 해독 · `0xB1` → `B1`, `0x04` → `4`, `0x00` → 미보고
14. 출입구 · `0x1E 02`가 더 이상 `call: true`를 만들지 않음
15. 재시도 금지 · `0x7F` 동작이 큐에 들어가지 않고 재시도되지 않음

## 12. 결정이 필요한 것과 남은 실측

### 확정된 결정

1. **`tx_quiet_ms` 기본값을 60으로 옮깁니다.** 사용자가 그 값으로 시험해 대부분의 손실이
   사라졌습니다. 남은 실패의 원인은 0.1절에서 셋으로 나누어 다룹니다.
2. **`0x7F` 출입구 버튼을 남깁니다.** 메인 월패드 다음에 서브폰을 구현할 예정이므로,
   다중 프레임 경로도 지우지 않고 격리만 합니다 (5절·7.3절).
3. **승강기 호출은 계측 실험으로 진행합니다** (6.3절). 확인 기계를 어차피 만들기 때문에
   추가 비용이 거의 없고, 한 번 누르면 확답이 나옵니다.

### 다음 실측

1. **`tx_quiet_ms` 60에서 캡처를 켜고 조명을 20회 조작.** 손상 구간을 세어 **남은 충돌이
   얼마인지** 잽니다. 4절의 재시도가 실제로 필요한지 판정하는 근거입니다.
2. **꺼져 있는 존에 목표 온도 설정.** `0x45`가 존을 켜는지 가릅니다 (1.1절).
3. **벨이 울리지 않는 상태에서 월패드 문열기.** `0x1E 02`가 명령인지 알림인지 가릅니다.
4. **호출에 응답하지 않고 종료될 때까지 캡처.** 같은 질문의 반대편입니다.

### 범위 밖

일괄소등 `0x2A`가 `40 10 00 <19> <조명군> <1B> <가스>` 형태로 조명군과 가스 상태를 함께 싣는
것을 이번 캡처에서 확인했습니다. 가스가 `03`에서 `04`로 바뀔 때 `0x2A`의 해당 바이트도 함께
바뀝니다. 해독 여지가 있으나 0.3.0 범위 밖입니다.

## 13. 이 설계의 한계

- 큐와 재시도는 `0.3.0`에서 구현되었으나(원장 `M4-E118`), 실제 버스에서 실행된 적은 없습니다.
- 가스에 직접 응답이 오는지 관측한 적이 없습니다. 폴링 확인을 전제로 설계했습니다.
- 승강기 호출 두 변형은 모두 근거가 없습니다. 6.3절은 성공을 기대하는 설계가 아니라 **판정을
  얻는 설계**입니다.
- 층 `0xB1`을 지하 1층으로 읽는 것은 표본 하나에 기댄 추정입니다.
- `tx_quiet_ms` 60에서 남은 실패의 원인 배분은 아직 측정되지 않았습니다. 0.1절의 세 후보는
  모두 코드에 실재하지만, 각각이 실패의 몇 할인지는 캡처를 다시 떠야 알 수 있습니다.
- `sevenFProofByStart`에 `household:ringing` 항목이 없어 세 매크로 중 하나는 서브폰 회선이
  붙어도 증적을 받을 수 없습니다. 0.3.0에서 고치지 않고 서브폰 작업으로 넘깁니다.
