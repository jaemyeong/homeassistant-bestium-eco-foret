# 가스 `0x1B` 실측 시나리오

작성 2026-08-30. 사용자가 "가스 닫기(열기는 못함), 가스 상태 체크"를 승인했습니다.
이 문서는 착수 전 검수를 위한 것입니다.

## 1. 왜 이 기기는 다른 기기와 다른가

지금까지 실측한 조명·난방·일괄소등은 전부 **누르면 되돌릴 수 있는** 기기였습니다.
잘못 보내도 반대 프레임 한 번이면 원상 복구입니다.

**가스는 그렇지 않습니다.** 차단은 보낼 수 있지만 여는 명령은 없습니다. 레거시 구현도
`04 = ON (지원되지 않음)`이라고 주석에 적어 두었습니다. 한 번 잠그면 **사람이 현장에서
손으로 열어야 합니다.**

그래서 이 시나리오는 다른 실측과 절차가 다릅니다. 되돌리기가 사람의 물리적 행동에
의존하므로, 그 행동을 할 준비가 되었을 때만 진행합니다.

## 2. 지금까지 확보한 근거

세 출처가 일치합니다.

| 프레임 | 뜻 | 근거 |
| --- | --- | --- |
| `f70b011b0143110000b5ee` | 질의 | 버스에서 **3,896회** 관측. 레거시 `makePacketQueryState`와 바이트 단위 일치 |
| `f70d011b04431100030000b5ee` | 상태 응답, `03` **잠김** | 3,843회 |
| `f70d011b04431100040000b2ee` | 상태 응답, `04` **열림** | 46회 (전부 원본 캡처, 즉 사용자가 가스를 쓰던 시각) |
| `f70b011b0243110300b5ee` | **차단 명령** | 원본 캡처에서 **1회** 관측. 월패드 자신이 보낸 것 |
| `f70b011b0443110303b0ee` | 차단 명령의 직접 응답 | 1회. `F7 0B 01 1B 04 43 11 <값> <상태> <XOR> EE` |

레거시 `makePacketSetState`는 `F7 0B 01 1B 02 43 11 XX 00 YY EE`를 만들고 `XX`가
`03`=차단, `04`=열기입니다. 계산한 차단 프레임이 관측된 것과 정확히 같습니다.

## 3. 현재 상태

**잠겨 있습니다.** 최근 실행의 마지막 상태 응답이 `03`이고, `batchoff2`를 포함한 24개
실행 전부에서 `04`(열림)가 **0회**입니다. 열림 46회는 모두 원본 캡처 시각의 것입니다.

이것이 시나리오를 두 단계로 나누는 이유입니다. 지금 차단을 보내면 **상태가 바뀌지
않습니다.** 전이를 볼 수 없습니다.

## 4. 안전 경계

- **여는 프레임 `f70b011b0243110400b2ee`는 어떤 단계에서도 보내지 않습니다.**
  `guard.ts`의 거부 목록에 있고 `--allow-all`로도 열리지 않습니다. 이 시나리오는 그
  거부를 건드리지 않습니다.
- 차단 프레임은 지금 **어느 허용 목록에도 없습니다.** 7단계로 추가해야 합니다.
- **차단 후 복구는 도구가 하지 못합니다.** 사용자가 현장에서 밸브를 열어야 합니다.
- **이 세대의 가스 밸브는 주방만 담당합니다 (사용자 확인, 2026-08-30).** 보일러 급기와는
  무관하므로 잠긴 동안에도 난방과 온수는 멎지 않습니다. B단계의 선행 질문이었고 답을
  받았습니다.

## 5. A단계 — 무위험, 지금 가능

**질문**: 이미 잠긴 밸브에 차단 명령을 보내면 기기가 응답하는가?

이것은 그 자체로 알 값어치가 있습니다. 애드온의 송신 확인이 "이미 그 상태인 명령도
확인된 것으로 친다"는 전제 위에 서 있는데, 가스에서 그 전제가 참인지 확인한 적이
없습니다.

| 단계 | 내용 |
| --- | --- |
| A1 | 관측 창을 열고 상태가 `03`인지 확인. 최소 10회 폴링 |
| A2 | 무장 없이 차단 프레임을 dry-run |
| A3 | 게이트 경유로 차단 프레임 1회 송신, `--expect f70b011b04431103` |
| A4 | 직접 응답 유무와 레이턴시 기록. 상태가 `03`으로 유지되는지 확인 |

**판정**
- 직접 응답이 오면: 이미 그 상태여도 기기가 응답한다는 것이 확인됩니다.
- 오지 않으면: 상태 변화가 없을 때는 응답도 없다는 뜻이고, 애드온의 확인 전략에
  영향이 있습니다. 그것도 결과입니다.

**위험**: 없습니다. 상태가 이미 목표값이라 바뀔 것이 없습니다.

## 6. B단계 — 전이 관측, 사용자의 물리적 조작 필요

**질문**: 열린 밸브에 차단을 보내면 실제로 잠기는가, 그리고 응답과 전이의 시간 관계는?

| 단계 | 내용 | 누가 |
| --- | --- | --- |
| B1 | ~~밸브 범위 확인~~ **완료: 주방 전용** | 사용자 |
| B2 | 밸브를 손으로 엶 | 사용자 |
| B3 | 상태 응답이 `04`로 바뀌는 것을 관측. 최소 5회 폴링 | 도구 |
| B4 | 게이트 경유로 차단 1회 송신, `--expect f70b011b04431103` | 도구 |
| B5 | 직접 응답, 상태 전이 `04` → `03`, 폴링 지연을 기록 | 도구 |
| B6 | **밸브를 손으로 다시 엶** | 사용자 |

**판정**: 폴링이 `04` → `03` 전이를 보고하면 확인입니다. 조명·난방과 같은 기준으로,
직접 응답은 더 약한 관측으로 남깁니다.

**중단 조건**
- B3에서 `04`가 관측되지 않으면 중단합니다. 밸브가 실제로 열리지 않았다는 뜻입니다.
- 사용자가 B6을 지금 할 수 없다면 B단계 전체를 미룹니다.

## 7. 허용 목록 변경

7단계에 프레임 **하나**를 추가합니다.

```
f70b011b0243110300b5ee    가스 차단
```

거부 목록은 건드리지 않습니다. 여는 방향은 그대로 막혀 있습니다.

시험으로 확인할 것:
- 6단계는 이 프레임을 여전히 거부한다.
- 7단계는 이 프레임만 추가한다.
- **여는 프레임은 7단계에서도, `--allow-all`로도 거부된다.**
- 값이 `03`이 아닌 어떤 가스 설정 프레임도 거부된다.

## 8. 기록

- 원장에 A단계와 B단계를 별도 행으로 남깁니다. 근거의 성격이 다르기 때문입니다.
- 명세 §2.3에 직접 응답 형태 `F7 0B 01 1B 04 43 11 <값> <상태> <XOR> EE`를 추가합니다.
  현재 명세에는 이 형태가 적혀 있지 않습니다.
- 상태 전이를 관측하면 `03`/`04`의 의미가 관측 1회에서 우리 송신으로 승격됩니다.

## 9. 이 시나리오가 답하지 않는 것

- 밸브를 여는 방법. 이 회선에 없고, 앞으로도 시험하지 않습니다.
- 차단이 주방만 막는지 보일러까지 막는지. B1에서 사용자에게 묻는 것이지 실측이
  아닙니다.
- 잠긴 상태를 오래 유지했을 때의 거동. B단계는 사용자가 다시 열 때까지의 짧은
  시간만 봅니다.
